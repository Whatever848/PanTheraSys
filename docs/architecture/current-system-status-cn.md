# PanTheraSys 当前系统状态扫描说明

更新日期：2026-04-21

## 1. 结论先行

当前 `PanTheraSys` 已经不是空项目，而是一个具备企业级原型底座的 Qt/C++ 治疗工作站项目。  
它已经具备：

- 可运行的桌面工作站壳层
- 可工作的核心安全联锁
- 可工作的临床数据仓储接口与 MySQL 持久化
- 可演示的监控、方案、治疗、数据管理四大页面
- 自动化测试与 QMS 起步文档

但它仍然是“工程原型 / 仿真原型”，还不是可用于人体治疗的医疗设备软件。  
如果目标是后续用于人体治疗，后续开发必须按“需求基线 + 风险控制 + 可追溯验证 + 真实硬件接入”的路线推进，不能只继续堆 UI。

## 3. 当前系统具备哪些功能

### 3.1 工程与架构底座

已具备并可用：

- CMake + Qt Widgets + C++20 的分层工程结构
- `ApplicationContext` 统一管理当前患者、当前方案、当前角色
- `EventBus` 事件总线
- `SafetyKernel` 安全联锁与模式状态机
- `AuditService` 审计事件采集
- `IClinicalDataRepository` 临床数据仓储抽象
- `SeedClinicalDataRepository` 种子数据仓储
- `MySqlClinicalDataRepository` MySQL 仓储实现
- `SimulationDeviceFacade` 设备仿真适配器

判断：这些不是空壳，核心类都有实际实现，且与 UI 已经接线。

### 3.2 设备监控模块

已实现：

- 设备实时快照显示
- 电源、水循环、运动、换能器、图像质量、输出功率等指标展示
- 水循环/功率/运动/急停故障注入
- 联锁状态实时联动

当前性质：

- 功能是真实现的
- 但数据源是 `SimulationDeviceFacade`
- 不是实际硬件采集

判断：`已开发完成（仿真级）`

### 3.3 治疗方案模块

已实现：

- 患者选择与当前患者上下文同步
- 图像采集路径管理
- 当前切片标注
- 基于标注区域生成治疗靶点
- 治疗参数编辑
- 方案草案生成
- 方案预览
- 方案编辑
- 方案保存到仓储
- 方案删除
- 方案审批/锁定
- 历史图像加载与对比
- 本地 PNG 导出
- 基于切片轮廓的三维重建预览
- 基于仿真快照的呼吸跟随补偿计算
- 功率曲线与覆盖率指标展示

当前性质：

- 页面逻辑很多是真实现的
- 方案保存可落到 `Seed/MySQL` 仓储
- 三维重建、呼吸跟随、靶点生成属于模拟/算法原型，不是真实临床算法链
- 图像采集不是来自真实超声设备，也不是 DICOM 接入

判断：`核心流程已开发，但属于仿真/原型级`

### 3.4 治疗执行模块

已实现：

- 读取当前患者的可执行方案
- 方案可选、可切换
- 开始/暂停/继续/终止治疗
- 进度推进
- 能量累计显示
- 日志输出
- 安全联锁拦截开始治疗
- 红色联锁触发时自动中止
- 与 `SimulationDeviceFacade` 的输出使能联动

当前性质：

- 真实存在执行状态机和交互逻辑
- 但执行过程仍是模拟推进
- 没有把执行过程自动沉淀为 `TreatmentSessionRecord`、`TreatmentRecord`、`TreatmentReportRecord`

判断：`已开发执行演示闭环，但未形成真实业务闭环`

### 3.5 数据管理模块

已实现：

- 患者列表、搜索、选中、详情展示
- 患者新增、编辑、归档
- 患者 CSV 批量导入
- 影像记录新增、编辑、删除
- 影像缩略图与预览
- 治疗记录新增、编辑、删除
- 治疗报告新增、编辑、删除
- 报告 HTML 预览
- 与当前患者、当前方案上下文联动刷新

当前性质：

- 这是当前项目里最完整的业务 CRUD 模块之一
- 既支持种子仓储，也支持 MySQL 持久化
- 但影像只是记录 `storagePath`，并没有真实采集链和医学影像管理能力
- 治疗记录/报告主要是“数据维护页”，不是治疗执行后自动生成

判断：`已开发完成（原型业务闭环）`

## 7. 下一步项目应该优先做什么

如果目标是把这个项目继续推进为“未来可用于人体治疗的软件项目”，建议按下面顺序做，而不是先继续加页面。

### 第一优先级：把业务闭环补完整

- 让治疗执行页在开始/结束治疗时自动生成并保存 `TreatmentSessionRecord`
- 在治疗推进过程中自动写入 `TreatmentRecord`
- 在治疗结束后自动生成初版 `TreatmentReportRecord`
- 让方案页导出的当前影像能够一键登记到 `image_series`
- 让审计日志从内存改为可持久化

原因：

- 现在的“方案页、治疗页、数据页”还是弱闭环
- 真正的企业级项目首先要做到数据链闭环，而不是只做演示链闭环

### 第二优先级：把“仿真链”替换成“真实接口链”

- 增加 DICOM/DCMTK 接入
- 增加真实超声图像读取与显示链
- 增加运动控制、功率控制、水循环、急停等实机适配器
- 保留仿真适配器，形成“仿真/实机”双模式

原因：

- 目前监控、采集、治疗都还依赖模拟设备
- 没有真实硬件接入，就无法进入真正的系统联调阶段

### 第三优先级：把安全与合规能力落地

- 登录、角色、权限控制
- 审批人、审批时间、电子签名留痕
- 配置版本管理
- 报警记录持久化
- 风险控制项和软件实现建立追溯关系

原因：

- 医疗设备软件不是“功能能跑起来”就够
- 后续如果面向人体治疗，这些都是必须项

### 第四优先级：扩展验证体系

- UI 层测试
- 方案算法测试
- 治疗执行状态机测试
- MySQL 之外的系统集成测试
- HIL 测试
- 异常恢复测试

原因：

- 现在测试主要覆盖核心基础层
- 对于后续医疗场景，这个覆盖面明显不够

## 8. 结合海扶类产品做参考时的建议

可以参考海扶类产品的功能分层方式，但不建议直接照搬界面或流程描述。  
更合理的做法是把需求收敛成你自己的产品分层：

- 患者与检查数据管理
- 图像采集与处理
- 病灶标注与三维评估
- 治疗方案设计与审批
- 治疗执行与联锁控制
- 设备监控与报警
- 审计、报表、权限与配置管理

然后每个功能都补齐：

- 需求编号
- 风险编号
- 设计说明
- 测试用例
- 审计点

这样项目才会从“演示型原型”走向“可交付的医疗设备软件工程项目”。

## 9. 一句话总结

当前项目最强的是：`工程底座 + 安全联锁 + 数据 CRUD + 仿真演示链`。  
当前项目最大的短板是：`真实影像链、真实硬件链、治疗数据闭环、权限审计落库、注册级验证体系`。
